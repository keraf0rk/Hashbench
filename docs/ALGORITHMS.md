<h1 align="center">🔐 Algorithms &amp; modes</h1>

<p align="center">Шпаргалка по режимам <code>-m</code> hashcat, форматам JtR и классам стойкости.</p>

## 🏷️ Режимы hashcat и аналоги в John

| `-m` | Алгоритм | JtR `--format` | Где встречается |
|------|----------|----------------|-----------------|
| 1000 | NTLM | `NT` | Windows (SAM, AD) |
| 1400 | SHA2-256 | `raw-sha256` | «голый» SHA-256 |
| 1410 | sha256($pass.$salt) | dynamic | SHA-256 с солью в конце |
| 1450 | HMAC-SHA256 (key=$pass) | `hmac-sha256` | HMAC-конструкции |
| 7400 | sha256crypt ($5$) | `sha256crypt` | Linux `/etc/shadow` |
| 8900 | scrypt | — | Litecoin, Ethereum-кошельки, Android |
| 34000 | Argon2 | — | современные веб-приложения |

> Имена форматов JtR **не совпадают** с числовыми `-m`. hashcat 7 умеет автоопределение: опусти `-m` или используй `--identify hash.txt`.

## 📈 Три класса стойкости

```
compute-hard   NTLM, SHA-256       только вычисления        GPU рвёт CPU в 30–200×
    │
iteration-hard sha256crypt, bcrypt N тысяч повторов         GPU впереди ~30×
    │
memory-hard    scrypt, Argon2      требуют RAM на хеш        GPU-преимущество исчезает
```

**Шкала стойкости к GPU-перебору (хуже → лучше):**

```
NTLM → SHA-256 → sha256crypt → bcrypt → scrypt → Argon2id
```

## 🧮 hashcat vs John the Ripper

| | hashcat | John the Ripper |
|---|---------|-----------------|
| Движок | GPU (CUDA/OpenCL/Metal) | CPU (OpenCL слабее) |
| Сила | максимальная скорость | гибкость, автодетект |
| Автоопределение хеша | частично (v7 `--identify`) | да |
| `*2john` экстракторы | нет | да (`zip2john`, `ssh2john`…) |
| CUDA в JtR | — | заброшен в 2019, только OpenCL |

**Связка на практике:**

```
┌─ JtR: извлечь хеш из файла ──┐      ┌─ hashcat: тяжёлый перебор на GPU ─┐
│  ssh2john id_rsa > hash.txt  │  →   │  hashcat -m <mode> hash.txt ...   │
│  + автоопределение формата   │      │  (быстрее на compute-hard)        │
└──────────────────────────────┘      └───────────────────────────────────┘
```

## 🧂 Зачем нужна соль

Соль **не замедляет** перебор одного хеша (1400 ≈ 1410 по скорости), но:

- убивает **радужные таблицы** (предрасчёт под конкретную функцию);
- убивает общие словари хешей и атаку «один хеш → много жертв».

Поэтому все современные схемы солёные. Подробнее о радужных таблицах — в [`RENTAL.md`](RENTAL.md).

## 🛡️ Рекомендация для хранения паролей

Для продакшена стоит выбирать **Argon2id** (текущая рекомендация OWASP) или scrypt — memory-hard делает бессмысленным даже GPU-ферму. Голый SHA-256 и тем более NTLM для хранения паролей не годятся.
